# PRD: Voice-to-Action Agent V2.4

## Context

具身智能产品的核心不只是让机器人“能听懂”，而是让机器人能把自然语言意图转化为可执行、安全、可反馈、可评估的任务流。V1 以家庭/服务机器人为模拟场景，验证语音/文本到任务执行的交互闭环。

## Goal

构建一个本地可运行的作品集原型，展示用户用自然语言下达物理世界任务后，Agent 如何完成：

- 指令理解
- 对象和位置抽取
- 歧义澄清
- 安全确认
- 动作计划生成
- 执行状态反馈
- 机器人语音反馈
- 语音交互脚本
- 语音反馈评估
- Grounding 证据展示
- 执行路径预览
- 路线重规划与绕行执行
- 路线质量评估
- 执行中暂停、改口和接管
- 异常/高风险接管
- 结果指标记录

## Target User

- 家庭服务机器人用户
- 机器人产品经理/交互设计面试官
- 希望看到“语音 Agent 到具身智能任务执行”能力迁移的招聘方

## User Jobs

- 用自然语言描述想让机器人完成的任务
- 在对象不明确时快速澄清
- 在高风险动作前确认或接管
- 在机器人执行中临时暂停、修改目标或改由人工接管
- 看到机器人当前理解、计划和执行状态
- 听到或看到机器人对关键状态的反馈话术
- 理解机器人每次反馈背后的系统状态和下一步选择
- 复盘任务是否成功以及失败原因

## V1 Scope

- 支持文本输入；浏览器支持时支持 Web Speech API 语音输入
- 支持固定家庭场景：客厅、厨房台面、门口、老人座位
- 支持对象：红色杯子、蓝色杯子、药盒、快递、椅子障碍、重箱子
- 支持任务类型：拿取放置、检查、递送、搬运
- 支持子 Agent 的决策链展示：Intent、Grounding、Safety、Recovery、Interruption、Planner、Evaluator
- 支持多模态指代雏形：颜色、区域、左右、老人旁边、门口等场景语义
- 支持用户点击场景对象后，用“这个/那个”进行上下文指代
- 支持对象歧义澄清
- 支持中/高风险任务确认
- 支持异常恢复：路径阻塞、药品敏感递送、避障恢复、人工接管
- 支持执行路径预览：路线分段、预计距离、预计耗时和路径风险点
- 支持路线重规划：将“绕开椅子走”等空间约束转化为绕行点
- 支持执行中用户打断：暂停、改目标位置、换目标对象、路线重规划、人工接管
- 支持 2D 场景执行动画和时间线
- 支持机器人语音反馈话术、播报开关和重播最近一句
- 支持语音交互脚本页，将系统状态、用户风险、反馈策略和指标建立映射
- 支持语音反馈评估集，用于验证关键状态是否触发正确话术
- 支持 Grounding 证据面板，用于解释对象选择和无对象导航判断
- 支持路线质量评估集，用于验证路径分段、绕行点、风险标记和策略标签
- 支持基础指标面板
- 支持评估集回归，用于验证关键任务流是否稳定
- 支持打断专项评估集，用于验证执行中动态意图处理是否稳定

## Non-goals

- 不做真实机器人控制
- 不接入 ROS/ROS2
- 不做完整 ASR/NLU/TTS 模型训练
- 不追求通用开放世界理解
- 不在 V1 接入真实支付、摄像头或家庭设备

## Functional Requirements

1. 用户输入自然语言指令后，系统需要展示结构化任务 JSON。
2. 当对象不明确时，系统需要提出澄清问题并提供候选对象。
3. 当任务涉及药品、重物、门口检查或用户明确要求小心时，系统需要进入安全确认。
4. 用户确认后，系统需要生成任务计划并在 2D 场景中模拟执行。
5. 用户选择人工接管时，系统需要停止自动执行并记录接管次数。
6. 系统需要记录总任务数、完成率、澄清次数、安全确认次数、人工接管次数、风险拦截次数。
7. 系统需要展示每个子 Agent 的判断依据，帮助面试官理解产品架构。
8. 系统需要支持一键运行评估集，并展示通过/未通过用例。
9. 系统需要将“椅子”等障碍物从目标对象中区分出来，作为安全约束或避障约束处理。
10. 系统需要在高风险执行中断时暂停任务，并给出恢复选项。
11. 系统需要在执行中识别用户打断，取消未完成动作并保留上下文。
12. 系统需要支持用户改目标位置或目标对象后重建任务计划。
13. 系统需要支持一键运行打断专项评估集，并展示通过/未通过结果。
14. 系统需要在理解、澄清、确认、执行、恢复、打断和接管节点生成用户可见的话术反馈。
15. 系统需要将关键语音反馈沉淀为可复盘脚本，覆盖低风险任务、歧义澄清、安全确认、异常恢复、中途改口和人工接管。
16. 系统需要支持语音反馈评估，验证关键状态触发的话术类型和内容是否符合预期。
17. 系统需要展示 Grounding 证据，包括候选对象、证据分、命中原因和最终选择。
18. 系统需要展示路径预览，包括路线分段、预计距离/耗时和风险点。
19. 系统需要支持执行中路线重规划，将用户的绕行约束转化为新的路线并逐段执行。
20. 系统需要支持路线质量评估，验证 direct、avoid_chair、navigation、elder handoff 等路线报告是否满足物理执行预期。

## UX Requirements

- 第一屏就是可操作工作台，不做营销落地页。
- 重点展示“用户说了什么、Agent 怎么理解、机器人怎么执行”。
- 对高风险任务要明确标识，不允许无提示自动执行。
- 指标要围绕任务完成和安全，而不是聊天轮次。

## Success Metrics

- V1 demo 能在 3 分钟内让面试官理解产品价值。
- 15 条基础评估任务中，至少 15 条能正确进入预期流程。
- 7 条打断评估任务中，至少 7 条能正确进入预期流程。
- 7 条语音反馈评估任务中，至少 7 条能触发预期话术类型和关键内容。
- 4 条路线质量评估任务中，至少 4 条能生成符合 expected 的路线报告。
- 用户能清楚看到每次澄清、确认、打断、恢复、接管和完成，并获得对应语音反馈话术。

## Risks

- 规则解析过于简单，容易被误认为技术含量不足。
- 如果只展示聊天，无法体现具身智能价值。
- 如果 UI 过重，会盖过产品逻辑。

## Mitigation

- V1 明确定位为产品原型，不是算法 benchmark。
- 文档中补充未来 LLM/VLM/ROS 扩展方案。
- Demo 中持续强调安全确认、任务流和指标闭环。
