Product Evolution Story

Voice-to-Action Agent 版本演进

这不是功能清单，而是一条产品判断链：先验证自然语言到任务流，再补齐 grounding、安全、恢复、打断和评估治理，逐步靠近具身智能产品经理需要负责的真实问题。

打开 Demo 产品介绍 核心验收
最终定位 自然语言意图 -> 可执行、安全、可恢复、可评估的机器人任务流
转型叙事 华为多 Agent 工作流工程经验 -> 语音/多模态 Agent PM -> 具身智能交互 PM
当前证据 主线收缩为产品介绍、主 Demo 和核心验收；历史材料与 LLM 实验页保留归档，不再抢占 Voice-to-Action 本体叙事。

Sequencing Logic

为什么按这个顺序迭代

01

先闭环

先证明用户一句自然语言可以变成结构化任务、计划、执行和指标，而不是一开始就追求复杂模型。

02

再处理真实世界复杂性

真实机器人会遇到指代不清、危险物品、路径阻塞、用户改口，所以逐步补 grounding、安全和恢复。

03

最后建立治理体系

Agent 产品不能只靠演示，要有评估集、打断专项测试和 expected vs actual 回放来保证行为稳定。

V2.3

路线重规划 / 绕行执行

产品问题：用户执行中说“绕开椅子走”时，系统是否真的改变路线，而不是只改一句提示？

  • 新增主动绕行策略：识别“绕开椅子/别撞障碍”等语言约束并加入绕行点。
  • 机器人按路线段逐段移动，携带物体跟随机器人，不再从取物点直接跳到终点。
  • 恢复策略中的“重规划路径”和执行中打断“绕开椅子走”都生成真实新路线。
  • 新增路线策略标签、绕行风险标记，以及基础/打断/语音三类回归用例。

体现能力：把多轮空间语言、路径规划、异常恢复和执行层状态机连成闭环。

路线质量评估 / 物理执行验收

产品问题：路线不是画出来就算完成，如何验收路径分段、绕行点、风险标记和策略标签是否符合物理执行预期？

  • 新增 `data/route-evaluation-set.json`，把 direct、avoid_chair、navigation、elder handoff 四类路线报告纳入回归。
  • 首页新增“运行路线质量评估”和“路线评估”指标卡，直接验证路径分段、绕行点、风险标记和策略标签。
  • 测试计划页新增路线筛选和 4 条路线用例，合并基础/打断/语音/路线四类回归，共 33 条可回放用例。
  • 修正无物体导航路线验收口径：移动到客厅仍保留障碍接近风险标记，避免把物理路线风险误判为完全低风险。

体现能力：把“机器人怎么走”从展示效果升级成可定义、可验收、可回归的产品质量标准。

面试时怎么讲

我做这个项目时没有一开始追求复杂模型，而是先验证具身交互产品的核心闭环：用户自然语言能否变成可执行任务。中间补过 grounding、安全确认、失败恢复、执行中改口、路线预览和行为评估，也做过语音、Tool Calling 和 LLM 接入桥实验。到 V11 后我主动收缩主线，只保留介绍页、主 Demo 和核心验收页；V11.3 继续把主 Demo 压成“一句话任务、家庭场景、任务状态”、四步核心流程和用户可理解的状态简报。

这条路线和我现在的多 Agent 工作流工程经验是连贯的：本质上都是把人的模糊意图转化为可执行、可解释、可评估的任务流。区别在于，这个项目把能力迁移到了具身智能场景，并且体现了产品经理需要做的取舍：不是功能越多越好，而是主流程越清楚越有说服力。
